\section{Choosing a generator for pretraining}\label{sec:scope}
Suppose you can afford to train a forecaster on two million synthetic
examples. Should you train on repeating waves from Waveform or on curves
drawn from Gaussian processes by KernelSynth? What matters is how well
the resulting model forecasts real series. Can we anticipate that choice
from what happens during training on each generator?

\emph{Epiplexity} gives one reason to try such an experiment. Consider a
wave with a repeating shape and fresh noise on each cycle. A forecaster
that learns the shape can reuse it on later cycles. Even with the shape
known, the individual noise values still cost bits to describe. Finzi et
al.\ formalize this intuition by asking which predictive program, within a
given time budget, minimizes the length of the program plus the expected
cost of encoding the data with it at a fixed precision. Epiplexity is the
length in bits of the program in this best two-part description~\cite{finzi2026}.

\texttt{episynth} lets us try the idea with a particular learner. In
\emph{prequential coding}, the forecaster predicts each new batch before it
learns from it. We add up its prediction losses and ask how much smaller
the total would have been at the final model's average loss rate. This
excess is a practical proxy for epiplexity. It follows one model and one
training procedure, so it depends on how quickly that learner improves.
Whether the acquired regularities help on real series is a question we can
test separately.

We work through the calculation on Waveform, then compare eleven generators
by both their training measurements and their real forecasting scores. At
the two budgets we studied, the prequential proxy alone gave little
guidance about which generator would transfer best.

For a comparison of your own, choose the target series and forecast horizon
first. Train on each candidate under the same settings, record its excess
loss, then score the frozen models on the same target windows. Repeating
this comparison across initializations lets you see how much the ranking
depends on a particular training run.

\section{Reading a learning curve on Waveform}\label{sec:waveform-example}
Waveform combines periodic waves with randomly drawn frequencies, amplitudes,
and phases. In the CPU example, the forecaster sees 16 or 32 past values
(the \emph{context}) and predicts the next 16 (the \emph{target}). Each such
pair is one forecast window. After installing \texttt{episynth}, run this
command from the repository root to train on 256 windows.
\begin{lstlisting}
python -m episynth.train --config publications/technical_report/examples/prequential.json --out build/report_demo/prequential
\end{lstlisting}

\subsection{What the area measures}\label{sec:prequential}
For each window $i$, the model assigns a density to the observed target
before training on that batch. Its negative log-likelihood (NLL), $\ell_i$,
is smaller when the model assigns a higher density. After training, we score
the final model on 128 fresh Waveform windows to estimate its average loss
$\bar\ell_f$. Using natural logs gives losses in nats. Dividing by $\ln 2$
converts them to bits. For $N$ training windows the library returns
\begin{equation}
 L=\frac{\sum_{i=1}^{N}\ell_i}{\ln 2},\qquad
 H=\frac{N\bar\ell_f}{\ln 2},\qquad S=L-H .
 \label{eq:area}
\end{equation}
$L$ is the cost accumulated while learning. $H$ is what the same number
of windows would cost at the final loss rate. Here their difference $S$
is 1,484.53 bits, or about 5.80 extra bits per training window.
Figure~\ref{fig:demo} shows how the difference builds up. Two learners
with the same final loss can have different areas if one takes longer to
reach it.

\begin{figure}[H]
\centering
\includegraphics[width=.88\linewidth]{figures/demo_loss.pdf}
\caption{Waveform at two budgets. In each upper panel the dashed line is the
final held-out loss. Batches above it add to the cumulative excess below,
and batches below it subtract. The archived curve averages 80 groups for
display. The totals use every batch.}
\label{fig:demo}
\end{figure}

Recover $S$ from the loss files using the final exponential moving average
(EMA) of the model weights.
\begin{lstlisting}[language=Python]
from episynth.estimators.prequential import PrequentialEstimator
run = "build/report_demo/prequential"
print(PrequentialEstimator(variant="ema").from_run_dir(run)["model_part_bits"])
\end{lstlisting}
\path{total_bits} and \path{data_part_bits} give $L$ and $H$. A negative
$S$ is possible. Encoding actual observations would also require a specified
precision and a lossless codec. \repolink{src/episynth/estimators/prequential.py}{Estimator source.}

\section{What did the forecaster learn?}\label{sec:methods}
A falling loss on Waveform has several possible explanations. A model could
learn the typical range of future values across the whole dataset, or it
could use the phase of a particular wave to forecast its continuation.
Both improvements contribute to the learning curve. Two further measurements
let us ask more specific questions of the same generator.

\texttt{episynth} implements prequential coding, requential coding, and
predictive $\mathcal V$-information. All three can use the same synthetic
generators, including Chaotic (Section~\ref{sec:data}).

\subsection{How much does the observed past help?}\label{sec:pvi}
Predictive $\mathcal V$-information measures how much access to the context
can reduce forecast log-loss for a chosen family of predictors
$\mathcal V$~\cite{xu2020}. We fit two models with the same initialization,
training windows, and normalization estimated from training targets. One
receives the context. The other sees neither its values nor its metadata.
Validation selects the best context-free checkpoint and makes it eligible
for the role with context as well. We score the selected predictors on
the same $M$ fresh test windows. On window $j$, their losses in nats are
$\ell_{\varnothing,j}$ and $\ell_{C,j}$, respectively. The paired gain is
\begin{equation}
 d_j=(\ell_{\varnothing,j}-\ell_{C,j})/\ln 2,\qquad
 \widehat I_{\mathcal V}=\frac1M\sum_{j=1}^M d_j,\qquad
 \widehat{\mathrm{SE}}=\frac{\operatorname{sd}(d_1,\ldots,d_M)}{\sqrt M}.
 \label{eq:pvi}
\end{equation}
A gain of one bit per window means that access to the past saves one bit of
forecast loss on average. The test estimate can be negative. Its standard
error describes variation across test windows for these fitted models.
In the CPU demo below, validation selected the context-free checkpoint for
both roles. Their predictions were identical, giving exactly zero gain.
\begin{lstlisting}
python -m episynth.train --config experiments/demos/v_information.json --out build/report_demo/v_information
\end{lstlisting}
The run checks that training, validation, and test seeds are disjoint and
records the selected checkpoints in \path{v_information.json}.
\repolink{src/episynth/estimators/v_information.py}{Estimator source.}

\subsection{How costly is it to teach a second predictor?}\label{sec:requential}
Requential coding uses a \emph{teacher} trained on windows from the
generator and a second model, the \emph{student}, that learns from the
teacher's sampled forecasts~\cite{qiu2026}. Given the same context, how
surprised is the student by a future the teacher draws? Direct mode scores
that future under both models before updating the student. The expected
log density ratio in bits is their Kullback--Leibler (KL) divergence.
Summing these estimates over the run measures how much the student's
predictions differed from the teacher's along the way.
\begin{lstlisting}
python -m episynth.train --config experiments/demos/requential.json --out build/report_demo/requential
\end{lstlisting}
The CPU demo used 32 real windows and 32 sampled horizons. It estimated a
total KL of 7.66 bits per student (Monte Carlo standard error 5.62 bits).
The estimated coding overhead was a separate 191.16 bits. Direct mode
reports those estimates. The finite ordered random coding mode
(\texttt{orc}) also writes the indices a decoder can replay.
\repolink{doc/source/measurements.rst}{Measurement guide.}

These quantities guide different follow-up experiments. For example, if a
generator has a large prequential area but a small gain from context, check
the context-free model's learning curve. Learning the overall distribution
of future values could explain part of the area. To find out whether those
predictions help on another dataset, we need forecasts on that dataset.

\section{Does the ranking predict transfer?}\label{sec:transfer}
We trained the same six-layer Moirai forecaster~\cite{woo2024} separately
on eleven generators, giving each about 2M or 40M windows. We then froze
the final EMA weights and scored forecasts on 55 short-horizon GIFT-Eval
tasks~\cite{aksu2024}. In this \emph{zero-shot transfer} setting the forecaster
sees the recent history of each real series and forecasts its future
without further training.

Our main score is the continuous ranked probability score (CRPS), which
assesses the whole forecast distribution. For each task we compare the
model with a seasonal na\"ive forecast that repeats values from the previous
season. We take the geometric mean of the 55 model-to-baseline CRPS ratios.
Lower is better, and one is a tie. The archive also reports mean absolute
scaled error (MASE) for the forecast median.

\begin{figure}[H]
\centering
\includegraphics[width=.84\linewidth]{../article/figures/transfer_results.pdf}
\caption{Each dot pairs a generator's prequential excess ($S\ln 2$, in
million nats) with its real-data CRPS ratio. If a larger area predicted
better transfer, the dots would fall from upper left to lower right.
The open marker repeats Waveform at 40M windows. Its CRPS ratio moves
from 1.373 to 0.972 with nearly the same area.}
\label{fig:transfer}
\end{figure}

At 2M windows, Waveform accumulated slightly more excess loss than
KernelSynth (70.9 versus 68.4
million nats). Both beat the seasonal baseline, but KernelSynth gave the
better real forecasts by CRPS (0.678 versus 0.818 for Waveform).

The follow-up fits match the original generator, budget, and initialization.
The context gains use 100,000 paired test windows per run. At 2M windows,
requential KL ranged from 8.65 to 13.49 million bits per student. At 40M,
ETS and Chaotic gained almost equally from context (403 and 402 bits per window), yet their CRPS ratios
were 0.717 and 1.285. All full-set intervals in Table~\ref{tab:coding-transfer}
include zero. Removing Chaotic and Waveform after inspecting the data gave
$\rho=-0.82$ for the 40M prequential area (interval $[-1.00,-0.28]$).
That result describes the nine retained generators.

\section{Generators and forecast windows}\label{sec:data}
\subsection{What the generators produce}
\texttt{episynth} implements eleven generator families for pretraining,
including Waveform for periodic patterns, GARCH for changing volatility,
and Chaotic for nonlinear dynamics.
\repolink{doc/source/generators.rst}{Generator catalog.}

Chaotic returns one coordinate of a Lorenz trajectory or a scalar
Mackey--Glass trajectory. Small errors in the state inferred from past
values can grow over the forecast horizon. To try Chaotic, add
\texttt{--set data.generator=chaotic} to the command in
Section~\ref{sec:waveform-example} and choose a fresh output directory.

\subsection{Series and forecast windows}
Each seed gives one series $x_{1:L}$, whether from a generator,
\texttt{Corpus}, or \texttt{Mixture}. Fix the horizon $h$ and the distribution
of context lengths across generators. The seed selects length $c$ and start $r$.
\begin{equation}
 C=x_{r:r+c-1}, \qquad Y=x_{r+c:r+c+h-1}.
\end{equation}
Window order and optional dequantization are reproducible across batch
sizes and worker counts. \repolink{src/episynth/windows.py}{Window construction.}

\begin{figure}[H]
\centering
\includegraphics[width=.90\linewidth]{figures/architecture.pdf}
\caption{Waveform series from seed 0 before dequantization. Color marks the
selected context and target within each generated series.}
\label{fig:windows}
\end{figure}

\subsection{Model inputs and predictive density}
Moirai groups observations into patches of $P$ values. A batch has shape
$B\times T\times P$, with $T=(c_{\max}+h)/P$ and maximum context length
$c_{\max}$. Masks exclude left padding and hide the forecast patches.
Only the target values enter the loss.

In prequential runs, context determines the location $\mu_C$ and scale
$\sigma_C$. The normalized forecast density $f_t$ mixes Student-$t$,
fixed-variance Gaussian, and log-normal components.
\begin{equation}
 q(Y\mid C)=\prod_{t=1}^{h}
 \frac{1}{\sigma_C}\, f_t\!\left(\frac{Y_t-\mu_C}{\sigma_C}\,\middle|\,C\right).
 \label{eq:model-density}
\end{equation}
The product treats future values as conditionally independent given the
context. The likelihood and sampler use the same normalization.
\repolink{src/episynth/model/moirai.py}{Model source.}

\section{Reproducing a training comparison}\label{sec:run}
Copy the configuration from Section~\ref{sec:waveform-example}, change
\texttt{data.generator}, and train in a fresh output directory. Keep the
model, initialization, windows per run, sampling rules, optimizer, and
checkpoint variant fixed. Use \texttt{estimator} to select a measurement
and \texttt{estimator\_config} for its options. \repolink{src/episynth/train.py}{Training CLI.}

\subsection{Batch updates and checkpoint evaluation}
For each window in batch $\mathcal B_k$, \texttt{Trainer} records the
pre-update loss $\ell_i=-\ln q_{k-1}(Y_i\mid C_i)$ in window order. The
optimizer takes a step on the mean loss per forecast point,
$(Bh)^{-1}\sum_{i\in\mathcal B_k}\ell_i$. The trainer then updates the EMA weights.

\begin{figure}[H]
\centering
\includegraphics[width=.94\linewidth]{figures/execution.pdf}
\caption{Losses used in the prequential estimate. Training batches are scored
before their updates. The final EMA checkpoint is evaluated on separate
held-out windows, and the mean is scaled to $N$ training windows.}
\label{fig:execution}
\end{figure}

Raw and EMA checkpoints share the held-out windows and evaluation precision.
Restarting restores both sets of weights, the optimizer, and the seed
position from \texttt{last.pt}.
\repolink{src/episynth/training.py}{Trainer implementation.}

\section{Checking the measurements}\label{sec:validation}
\subsection{A forecast with a known answer}\label{sec:ou}
In the Ornstein--Uhlenbeck (OU) generator, each series follows a stationary
Gaussian AR(1) process with a coefficient drawn from a known prior.
Integrating over the coefficient gives the marginal density $M(x)$ of a
segment. The joint forecast $M(C,Y)/M(C)$ accounts for dependence among
future values. The pointwise forecast $\prod_t p(Y_t\mid C)$ uses the
same marginals and matches Moirai's factorization in Eq.~\eqref{eq:model-density}.
Use the latter as a reference for a model with that factorization.
\repolink{src/episynth/checks/ou_bayes.py}{Bayesian likelihood functions.}

On 64 OU windows with dequantization disabled, the joint forecast scored
14.3602 nats per window and the pointwise forecast scored 20.3312. Modeling
dependence among future values saved 5.97 nats per window on average.
Increasing the quadrature resolution from 512 to 1,024 nodes changed either
score by at most $2.35\times10^{-5}$ nats on any window.
\repolink{publications/technical_report/run_examples.py}{Example runner and checks.}

\subsection{Register a generator}
For a source outside the registry, implement \texttt{\_batch(seeds)} with
one series per seed. Here each series has a 24-point period and its own phase.
\begin{lstlisting}[language=Python]
import numpy as np
from episynth.generators import Generator

class RandomPhaseSine(Generator):
    name = "random_phase_sine"
    def _batch(self, seeds):
        phases = np.array([
            np.random.default_rng(int(seed)).uniform(0, 2 * np.pi)
            for seed in seeds
        ])
        time = 2 * np.pi * np.arange(self.length) / 24
        return np.sin(phases[:, None] + time[None, :])
\end{lstlisting}
Import the class in \path{src/episynth/generators/__init__.py}, add it to
\texttt{GENERATORS}, and set \texttt{data.generator} to
\texttt{random\_phase\_sine} for the CLI. An estimator can also receive the
generator instance directly.
\repolink{src/episynth/generators/__init__.py}{Generator registry.}

\subsection{Reporting an additional diagnostic}
Implement \texttt{run(model, generator, spec, config, out\_dir)} and return a
JSON-compatible result with declared units. This example reports the final
held-out loss $H/N$ in bits per window.
\begin{lstlisting}[language=Python]
from episynth.estimators import build, register

@register("endpoint_nll")
class EndpointNLL:
    def run(self, model, generator, spec, config, out_dir):
        area = build("prequential")
        result = area.run(model, generator, spec, config, out_dir)
        return {"bits_per_window": result["data_part_bits"] / result["n_windows"]}
\end{lstlisting}
Import this module before calling \texttt{build("endpoint\_nll")}. For CLI
use, import it through the registry and set \texttt{estimator} to \texttt{endpoint\_nll}.
